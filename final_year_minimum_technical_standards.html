Final-Year Software Development

Minimum Technical Standards

A practical reference for the technical, architectural, security, testing, deployment, documentation, and professional standards expected of final-year software development projects.

Purpose

The purpose of these guidelines is to establish a minimum technical standard expected of final-year software development projects.

Students are expected to demonstrate more than the ability to build a working application. A final-year project should provide evidence that the student understands modern software development practices, application architecture, security, data management, testing, deployment, source control, documentation, and software quality.

The complexity and implementation details of individual projects will vary. Where a student wishes to use an alternative technology, architecture, library, framework, or approach to those suggested in this document, this should be discussed with the project supervisor.

Students must be able to explain and justify the major technical decisions made during the development of their project.

1Acceptable Development Approach⌄

1.1 Low-Code, No-Code and UI-Generation Tools

Final-year software development projects must demonstrate substantial software development and software engineering work carried out by the student.

Applications that are built primarily using low-code, no-code, drag-and-drop, visual application builders, or automated UI-generation tools will not be accepted as final-year software development projects.

This requirement is particularly important for mobile application projects, where a wide range of platforms can generate substantial parts of an application without requiring the student to implement the underlying software.

Examples of tools and approaches that require particular caution include:

  • AppGyver and similar low-code application platforms.
  • Visual application builders.
  • Drag-and-drop mobile application development platforms.
  • Tools that automatically generate most of the application's screens, navigation, data access, or business logic.
  • AI or template-based systems that generate a substantially complete application from prompts or configuration.
  • UI-generation workflows that remove the need for the student to implement the application's user interface and behaviour directly.

Frameworks and development tools may, of course, provide scaffolding, components, libraries, templates, and development assistance. However, there must remain substantial evidence that the student has personally designed and implemented the application's:

  • User interface.
  • Application logic.
  • Data flow.
  • Navigation.
  • State management.
  • Validation.
  • Integration logic.
  • Security.
  • Error handling.

Mobile Development

For mobile applications, students should use recognised software development frameworks and demonstrate meaningful implementation using code.

Suitable examples may include:

  • .NET MAUI.
  • React Native.
  • Flutter.
  • Native Android development.
  • Native iOS development.
  • Other supervisor-approved development frameworks.

Tools such as Expo may be used where they act as part of a normal coded development workflow, for example as tooling around a React Native application.

However, students must not rely on Expo-based application generators, visual builders, templates, or similar tooling to generate the majority of the application's interface or functionality.

The distinction is important:

Using a framework or development tool is acceptable. Using a tool that effectively builds the application on the student's behalf is not.

Supervisor Approval

Where there is uncertainty about whether a particular platform, UI builder, code generator, AI development environment, or application-generation tool is acceptable, students must obtain approval from their supervisor before committing to that technology.

The supervisor may require the student to demonstrate:

  • Which parts of the application are manually implemented.
  • Which parts are generated.
  • What code the student is responsible for.
  • How much technical control the student retains over the application.
  • Whether the project provides sufficient opportunity to demonstrate final-year software engineering ability.

A project may be rejected if its chosen development approach substantially limits the student's ability to demonstrate programming, architecture, testing, debugging, security, and technical understanding.

2User Management & Security⌄

2.1 User Management

All projects that involve users must demonstrate an ability to manage application users.

The application must provide an administrative interface or dashboard that enables authorised users to:

  • Create users.
  • View users.
  • Update user details.
  • Remove or deactivate users.

Where appropriate, additional functionality may include:

  • Resetting user access.
  • Assigning or changing roles.
  • Locking or disabling accounts.
  • Viewing basic account status information.

Third-party user-management platforms may be used, but their use must be approved by the project supervisor.

2.2 Authentication

Students must not implement their own authentication mechanism.

Authentication must use an established and well-supported framework, library, or identity-management platform.

Suitable examples include:

  • ASP.NET Core Identity.
  • Keycloak.
  • Microsoft Entra ID / Entra External ID.
  • Auth0.
  • Other supervisor-approved solutions.

Where appropriate, the use of a dedicated identity provider such as Keycloak is encouraged.

Students must not create their own mechanisms for:

  • Password hashing.
  • Password storage.
  • Credential validation.
  • Authentication token generation where an established solution is available.
  • Session security.

2.3 Authorisation

The project must demonstrate authorisation as well as authentication.

At a minimum, applications should normally distinguish between two levels of access, for example:

  • Administrator.
  • Standard User.

More complex applications may use additional roles or permission-based access control.

Students must demonstrate that users cannot access functionality for which they do not have permission.

2.4 Protected Routes and Resources

Privileged routes and application resources must be protected.

Students must demonstrate that:

  • Unauthenticated users cannot access protected functionality.
  • Authenticated users cannot access functionality outside their assigned permissions.
  • Administrative functionality is available only to appropriately authorised users.
  • API endpoints are protected where appropriate.
  • Access control is enforced on the server or API.

Simply hiding a menu item, button, screen, or client-side route is not considered sufficient access control.

2.5 Token and Session Expiry

Applications must demonstrate appropriate token and/or session management.

Students must demonstrate:

  • Token or session expiry.
  • Appropriate handling of expired authentication.
  • Prevention of continued access after authentication has expired.
  • Re-authentication where appropriate.

Students should be able to explain:

  • What authentication mechanism is being used.
  • What tokens or sessions are created.
  • How long they remain valid.
  • What happens when they expire.

2.6 Security

Projects should follow recognised secure-development practices.

Students should consider areas such as:

  • Input validation.
  • Protection against SQL injection.
  • Cross-site scripting.
  • Cross-site request forgery where applicable.
  • Secure handling of credentials and secrets.
  • Appropriate HTTP security configuration.
  • Principle of least privilege.
  • Secure error handling.
  • Protection of sensitive data.

Secrets, API keys, passwords, connection strings, or other credentials must not be committed directly to source control.

3Application Architecture⌄

Students must demonstrate that their application has been designed rather than simply assembled as development progresses.

3.1 Separation of Responsibilities

Applications should demonstrate appropriate separation of concerns.

Depending on the technology used, this may include separation between:

  • Presentation/UI.
  • Business or application logic.
  • Data access.
  • External integrations.
  • Authentication and security.
  • Infrastructure concerns.

Large amounts of business logic should not reside directly inside controllers, UI components, or views.

3.2 Architectural Structure

Students should adopt an architecture appropriate to the size and complexity of the project.

Possible approaches include:

  • Layered architecture.
  • Clean Architecture.
  • Vertical Slice Architecture.
  • Modular monolith.
  • Client/server architecture.
  • Other recognised architectures.

Students are not required to use a particular architecture solely for the sake of complexity.

The architecture chosen should be appropriate to the project.

3.3 Dependency Management

Applications should make appropriate use of:

  • Dependency injection.
  • Interfaces and abstractions where they provide value.
  • Configuration management.
  • Reusable services and components.

Students should avoid unnecessary duplication and excessive coupling between application components.

3.4 Maintainability

Code should demonstrate:

  • Meaningful naming.
  • Logical organisation.
  • Appropriate class and method sizes.
  • Reuse where appropriate.
  • Avoidance of unnecessary duplication.
  • Consistent coding conventions.

Students should be able to explain the major components of their application and how those components interact.

4Data Management⌄

Most projects will be expected to demonstrate meaningful persistent data storage.

4.1 Persistent Storage

Applications should use an appropriate persistent data-storage technology such as:

  • Relational database.
  • Document database.
  • Cloud-hosted database.
  • Other supervisor-approved data-storage mechanism.

Examples include SQL Server, PostgreSQL, MySQL, SQLite, MongoDB, Cosmos DB, or equivalent technologies.

4.2 Data Modelling

Students must demonstrate appropriate data modelling.

This should include consideration of:

  • Entities or documents.
  • Relationships.
  • Primary identifiers.
  • Required and optional values.
  • Appropriate data types.
  • Data constraints.
  • Referential integrity where applicable.

4.3 CRUD Operations

The application should normally demonstrate meaningful:

  • Create.
  • Read.
  • Update.
  • Delete or deactivate.

operations against application data.

CRUD operations should form part of genuine application functionality rather than existing solely to satisfy this requirement.

4.4 Validation

Data must be validated appropriately.

Validation should occur at appropriate boundaries and should not rely exclusively on client-side validation.

4.5 Database Management

Students should demonstrate an appropriate approach to database creation and change management.

Where supported by the chosen technology, this may include:

  • Database migrations.
  • Schema versioning.
  • Seed data.
  • Deployment scripts.

4.6 Sensitive Data

Sensitive information should be stored appropriately.

Students must be able to explain which data within their application is sensitive and what measures have been taken to protect it.

5Functional Requirements⌄

The project must solve a clearly identified problem and provide meaningful functionality.

5.1 Core Functionality

The final system must contain sufficient functionality to demonstrate final-year development ability.

The project should not consist primarily of:

  • Static information pages.
  • Simple CRUD screens.
  • A direct copy of a classroom tutorial.
  • A thin user interface over a single third-party API.

CRUD functionality may form part of the project but should normally support a broader business or application workflow.

5.2 Business Logic

Projects should contain meaningful application or business logic.

Examples may include:

  • Rules.
  • Calculations.
  • Workflows.
  • Scheduling.
  • Approval processes.
  • Data transformation.
  • Search or filtering.
  • Notifications.
  • State transitions.
  • Reporting.

5.3 Error Handling

Applications must deal appropriately with expected error conditions.

Users should receive meaningful feedback rather than raw system exceptions.

5.4 Configuration

Environment-specific values should be configurable rather than hard-coded.

Examples include:

  • API URLs.
  • Connection strings.
  • Feature settings.
  • Authentication settings.
  • External service configuration.
6API / Integration⌄

Where appropriate, students should demonstrate interaction between separate software components.

6.1 API Development

Projects that expose an API should follow established HTTP and REST conventions where applicable.

Students should consider:

  • Appropriate HTTP verbs.
  • Appropriate status codes.
  • Request and response models.
  • Validation.
  • Authentication.
  • Authorisation.
  • Consistent error responses.

6.2 API Documentation

APIs should be documented using an appropriate mechanism such as:

  • OpenAPI.
  • Swagger.
  • Equivalent API documentation tooling.

6.3 External Services

Projects are encouraged to integrate with at least one external or independently deployed service where this provides genuine value.

Examples include:

  • External APIs.
  • Payment systems.
  • Mapping services.
  • Messaging services.
  • Email services.
  • Cloud services.
  • Identity providers.
  • AI services.

Students must understand what data is being exchanged with external systems.

6.4 Integration Failure

Applications should handle external-service failure appropriately.

A temporary failure of an external API should not result in uncontrolled application failure.

7Testing & Quality⌄

Testing must form part of the development process and must not be treated solely as a final-stage activity.

7.1 Automated Testing

Projects should contain automated tests appropriate to the application.

These may include:

  • Unit tests.
  • Integration tests.
  • API tests.
  • End-to-end tests.

7.2 Meaningful Tests

Students should concentrate testing effort on meaningful application behaviour.

Tests should cover areas such as:

  • Important business rules.
  • Validation.
  • Authorisation.
  • Data access.
  • Critical workflows.
  • Error conditions.

A large number of trivial tests is not necessarily evidence of good testing.

7.3 Test Organisation

Tests should be:

  • Repeatable.
  • Understandable.
  • Independent where possible.
  • Maintained alongside the application.

7.4 End-to-End Testing

Where appropriate, students should demonstrate automated testing of significant user workflows using tools such as:

  • Playwright.
  • Cypress.
  • Selenium.
  • Equivalent technologies.

7.5 Code Quality

Students should make reasonable use of:

  • Compiler warnings.
  • Static analysis.
  • IDE inspections.
  • Formatting tools.
  • Code reviews where applicable.

The submitted project should not contain large quantities of unresolved warnings or obviously dead code.

8Source Control & Development Process⌄

8.1 Source Control

All projects must use Git or another supervisor-approved version-control system.

The project repository should demonstrate continuous development throughout the project.

8.2 Commit History

Students should make regular, meaningful commits.

Commit messages should describe the change made.

Projects should avoid:

  • A single final commit containing most of the application.
  • Large numbers of meaningless commits such as update, fix, or changes.
  • Committing generated files unnecessarily.
  • Committing secrets.

8.3 Branching

Students should demonstrate an appropriate branching strategy.

This does not need to be unnecessarily complex.

Possible approaches include:

  • GitHub Flow.
  • Trunk-based development.
  • Feature branches.

8.4 Issue / Task Management

Students should maintain a record of project work using an appropriate system.

Examples include:

  • GitHub Issues.
  • Jira.
  • Azure DevOps.
  • GitLab Issues.
  • Equivalent project-management tooling.

Tasks should show evidence of planning and incremental development.

8.5 Pull Requests

Where practical, students should demonstrate familiarity with pull requests or merge requests.

This may include reviewing their own changes before merging where the project is individually developed.

9Deployment & DevOps⌄

A final-year project should demonstrate that the application can operate outside the student's development environment.

9.1 Deployment

The completed application should normally be deployed to an environment that can be demonstrated independently of the developer's machine.

Possible deployment environments include:

  • Azure.
  • AWS.
  • Google Cloud.
  • Docker-based hosting.
  • University infrastructure.
  • Other supervisor-approved platforms.

9.2 Build Process

The project should have a documented and repeatable build process.

Another developer should be able to obtain the source code and determine how to build and run the application.

9.3 Continuous Integration

Projects should, where feasible, include a CI pipeline.

The pipeline may perform activities such as:

  • Restore dependencies.
  • Compile/build.
  • Run automated tests.
  • Perform static analysis.
  • Produce deployment artefacts.

9.4 Continuous Deployment

Automated deployment is encouraged where appropriate but may not be mandatory for every project.

9.5 Environment Configuration

Students should demonstrate a clear distinction between environments where appropriate, for example:

  • Development.
  • Test.
  • Production.

Secrets and environment-specific configuration must be managed securely.

9.6 Containers

Containerisation using technologies such as Docker is encouraged where it provides genuine value.

Students using containers must understand how their containerised application operates.

10Documentation⌄

Documentation must be sufficient for another technically competent person to understand, build, run, and evaluate the project.

10.1 README

The repository should contain a clear README containing, at minimum:

  • Project purpose.
  • Main features.
  • Technologies used.
  • Prerequisites.
  • Installation instructions.
  • Configuration requirements.
  • Build instructions.
  • Run instructions.
  • Testing instructions.
  • Deployment information where relevant.

10.2 Architecture Documentation

Students should provide an overview of the system architecture.

This may include diagrams showing:

  • Major components.
  • Databases.
  • APIs.
  • External systems.
  • Authentication services.
  • Communication between components.

10.3 Database Documentation

Where appropriate, students should provide:

  • ER diagrams.
  • Schema diagrams.
  • Document structures.
  • Data-model descriptions.

10.4 API Documentation

APIs should be documented sufficiently for another developer to understand how they are used.

10.5 Design Decisions

Students should document significant architectural or technical decisions and provide the reasoning behind them.

11UX & Accessibility⌄

Applications should demonstrate that consideration has been given to the people who will use them.

11.1 User Experience

Interfaces should be:

  • Consistent.
  • Understandable.
  • Navigable.
  • Responsive where appropriate.
  • Designed around expected user workflows.

11.2 User Feedback

Applications should provide appropriate feedback for:

  • Successful operations.
  • Invalid input.
  • Failed operations.
  • Loading or long-running operations where relevant.
  • Authentication or authorisation failures.

11.3 Forms

Forms should demonstrate:

  • Clear labels.
  • Appropriate controls.
  • Validation messages.
  • Preservation of appropriate user input after validation failure.
  • Suitable defaults where relevant.

11.4 Accessibility

Students should demonstrate awareness of accessibility.

Consideration should be given to areas such as:

  • Keyboard navigation.
  • Semantic HTML.
  • Labels for form controls.
  • Colour contrast.
  • Alternative text.
  • Focus indicators.
  • Screen-reader compatibility.

Projects should aim to follow relevant WCAG principles where practical.

11.5 Responsive Design

Web-based applications should provide an acceptable experience across a reasonable range of screen sizes unless the nature of the project makes this inappropriate.

12Project Demonstration & Technical Understanding⌄

The final demonstration is intended to assess both the completed system and the student's understanding of the system they have developed.

12.1 Demonstration

Students should be able to demonstrate the important workflows of their application.

The demonstration should include more than the successful or "happy" path.

Where appropriate, students should demonstrate:

  • Authentication.
  • Different user roles.
  • Protected functionality.
  • Validation.
  • Error handling.
  • Important business processes.
  • Data persistence.
  • External integrations.
  • Testing.
  • Deployment.

12.2 Technical Understanding

Students must be able to explain the code and technologies used within their project.

Students should be prepared to explain:

  • Application architecture.
  • Authentication and authorisation.
  • Data modelling.
  • API design.
  • Testing strategy.
  • Deployment approach.
  • Important libraries and frameworks.
  • Security decisions.
  • Significant technical challenges.

12.3 Design Decisions

Students should be able to justify significant decisions.

For example:

  • Why a particular database was selected.
  • Why a particular architecture was chosen.
  • Why a specific authentication system was used.
  • Why particular technologies were selected.
  • What alternative approaches were considered.

12.4 Limitations

Students should be able to identify weaknesses or limitations in their own solution and describe how they would improve the system if development continued.

12.5 Third-Party and AI-Assisted Development

Students remain responsible for all code submitted as part of their project.

Where third-party libraries, code-generation tools, tutorials, AI assistants, or other external resources have been used, students must still be capable of explaining the resulting implementation.

The inability to explain significant sections of the submitted system may be treated as evidence that the student has not demonstrated the required technical understanding.

•Overall Principle⌄

A final-year project should demonstrate the student's ability to design, develop, secure, test, document, deploy, and explain a substantial software system.

The assessment should consider not only whether the software works, but also how it has been designed and engineered.

The use of modern libraries, frameworks, cloud platforms, identity providers, AI tools, and third-party services is encouraged where appropriate. However, students must understand the technologies they use and remain responsible for the architecture, implementation, security, testing, and quality of the completed system.
